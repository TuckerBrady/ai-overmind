## FEATURE 3 — SPLINTER TWINS (IN-SESSION)

Not every task deserves a mission brief. When the human needs something quick from a specialist's domain — a question answered, a file reviewed, a small artifact drafted — spawn a **twin** instead of dispatching.

A twin is a subagent (the `splinter-twin` agent shipped with this plugin) that hydrates itself from the specialist's own files at spawn time. When the team engine is connected (the `overmind-mcp` server; its tools show up as `mcp__overmind__*`), the twin calls `boot` with the seat name and gets the specialist's BOOT.md with every `@` import inlined. Without it, the twin reads BOOT.md and each imported file by hand. Either way it takes the `## Persona` section as its voice (falling back to a legacy `feedback_[name]_persona.md` only if that BOOT.md has no Persona section), does the task in their voice and to their standards, returns a report signed "[Name] (twin)", and dissolves. The real specialist's session, memory, and files are untouched. A twin skips the boot layer's session-start sequence entirely: it is not a session.

**How to spawn one:** invoke the agent by its full plugin-scoped name, `ai-overmind:splinter-twin` (the Agent tool's `subagent_type`), never a generic agent with a twin prompt: only that name carries the twin's tool allowlist and trips the twin guard. Give it a prompt that names the specialist, gives their seat name and the absolute path to their folder, and states the task. The seat name lets the twin boot through the team engine; the folder path is its fallback. Example prompt: *"You are a twin of Sam, Data Analyst. Seat: Sam. Their folder: [team-root]/Sam - Data Analyst/. Task: sanity-check the utilization math in [file] and flag anything off."*

**Twin vs. dispatch — the test:**
- Fits inside this session, needs only what's in the specialist's files, no follow-up state → **twin**
- Produces real deliverables, needs their browser/tools/session memory, runs long, or the human will ask about it later → **dispatch**

Twins never write to the specialist's HANDOFF.md, INBOX.md, mission-complete files (legacy mission-complete.md included), the Gopher Registry, or the Mission Board (see Splinter Twins and Gopher in gopher.md). That is enforced, not only asked: `agents/splinter-twin.md` carries a `tools:` allowlist, and the plugin's twin guard (`hooks/twin-guard.sh`) watches every twin tool call.

#### The twin guard is a seatbelt, not a sandbox

It protects the team against a **misled** twin: one that read a planted instruction, or got its task wrong, and reaches for a file it should never touch. It does not contain a determined program, and it does not pretend to.

- **Protected files:** every `INBOX.md`, `HANDOFF*.md`, `BOOT.md`, `CLAUDE.md`, `WORKING_WITH_*.md`, `mission-complete*.md`, `GOPHER_REGISTRY.md`, `MISSION_BOARD.md`, `team.db`, `_twin-guard.log`, and anything under `_claims/`, `.go-claim/` or `_ids/`.
- **Before the call (PreToolUse):** a twin's Write or Edit on a protected file is denied. A twin's Bash command is denied when it targets one (redirects, cp/mv/ln/install/rsync on any argument, tee, rm, sed -i and the like), names one outside a read-only verb (cat, grep, head, tail, wc, diff, less, awk or sed without -i, git log/show/diff/status), names one or `_Team` in an interpreter (python, node, perl, ruby, bun, deno, uv, cmd, powershell, sqlite3, ed, vim, patch, tar, xargs, `sh -c`), uses eval or source (read as bash reads the command word, so quotes and backslashes such as `e\val` don't hide it, and `coproc`, `if`, `while` and the like are skipped), redirects to a `$`-built target, gives a write command an argument built by a command substitution (backticks or `$(`), or names the guard's own record folder `ovm-twin-guard`. Hook input over 512 KiB is read whole once to find `agent_type`, because a cut input can hide it: a twin's call fails closed (its PostToolUse over the cap is alerted instead), and a main session is never refused. If no `agent_type` key turns up (including when reading the input fails first), the call is a main session's and passes. On bash older than 4.1 (macOS) the input is saved to a private temp file first, so no byte past the cap can be lost to a read-ahead. A `.` counts as `source` only when it starts a command outside quotes, so perl's `q(a) . q(b)` passes.
- **After a Bash call (PostToolUse):** before each twin Bash call the guard records a sha256 of every protected file under each team root it finds, and compares after the call. After the call it first re-hashes the files it recorded and logs any change at once, then walks for files added or removed, so a command that floods the tree with new files can't hide an edit behind a walk that outruns the hook's timeout. If a check is cut off anyway, this twin's next call is denied once with `TWIN-GUARD ALERT: previous check did not finish`. A change made by that Bash command produces `TWIN-GUARD ALERT: protected file changed during twin command: <path>`, shown next to the tool result and appended to `[team-root]/_twin-guard.log` (under the root the record was taken in, and under the root found after the call). If the call's own record was removed, it says `TWIN-GUARD ALERT: snapshot missing`; if the record says no team root was found but one resolves after the call, it says so. Every protected file is hashed again on every check, before and after each call: file times and sizes are never taken as proof that a file is unchanged, since a program can set them back after an edit. It never restores the file: another session may have written it legitimately in the same window. `_claims/` is not compared, because TARS rewrites it every turn. Write and Edit calls are not snapshotted: they are denied by path before they run (8.3 short names such as `MISSIO~1.MD` included).
- **Where it looks:** a team root is a folder holding a live `MISSION_BOARD.md` among the twin's working directory and up to three folders above it, and the session's project folder and up to three folders above that. Every such root is watched, except one inside another (the outer one covers it), so a working directory and a project folder in different teams are both checked. A `MISSION_BOARD.md` whose first line says `RETIRED BRIDGE COPY` (the pointer kept in each seat folder) never counts. Protected names match at any depth below it, except under `drafts/`, `.git/`, `node_modules/`, `_claims/` and any folder that holds a `.git` (a repo clone), unless that folder also holds a `BOOT.md`: a seat folder kept in git is still watched, with only its `.git` skipped. With no team root in reach, the detector is off and only the pre-check runs. The hook has 10 seconds: a snapshot that takes more than 5 is logged as `detector over budget`, and a snapshot cut off by the timeout checks nothing.
- **The orchestrator's rule:** after every twin, the orchestrator reads `[team-root]/_twin-guard.log` itself and never relies on the twin's own report. A twin result with a TWIN-GUARD ALERT in the log, or in its output, is **quarantined**. Don't act on it, merge it, or pass it on until the human or the orchestrator has reviewed the diff of the named file.

**Residual risks, stated plainly.** The detector sees only what a twin Bash command changed while it ran, under the team root, in the protected set, outside the pruned folders. It does not see a command left running in the background after the call returns, protected files in another team or outside the root, files under `drafts/` or inside a repo clone, or anything when no team root is in reach. A walk that outruns the hook timeout still has its recorded files checked first, but new files past that point go unseen (the next call reports the unfinished check). A program that finds and rewrites the call's snapshot record (same user, same machine) can hide its change: the record folder is private to the user (mode 700), not to the guard. A program that builds a protected path at run time gets past the pre-check, and is only reported afterwards. A Write through a symlink that points at a protected file is not caught before the call. The detector sees that a file changed, not who changed it, so a legitimate write by another session in the same window also alerts. And a twin spawned under any name other than `ai-overmind:splinter-twin` is not a twin to the guard at all. Every change to these checks must keep denying everything the v4 guard (fb649ac) denied; `tests/rel/test_no_regression.sh` holds that over a corpus of several hundred commands. The command-text checks read bash by pattern, not with a bash parser: any construct they misread is a residual, caught (if at all) only by the outcome check. The guard is defense in depth against a misled in-house twin, not a security boundary; the real controls are the kernel's trust boundary, the per-mission merge gate, and the human's yes on outward actions.

If the roster has no specialist for the domain, don't fake one with a twin — twins hydrate from real specialist files or not at all. Handle it yourself or propose a roster addition.

### Worker tiers — the right model and effort for the job

Not every twin or dispatched session needs the same horsepower. (Borrowed from Claude Managed Agents, where an orchestrator hands reading-heavy work to a cheaper worker.) Three tiers, each a model plus an effort level. **The Overmind picks the tier itself, from the task, without asking the human**, and writes it into the brief with a one-line reason. In a brief, that tier is advisory: switching a dispatched session's model needs the human's yes.

| Tier | Use it for | Twin (Agent tool `model`) | Dispatched session (model · effort) |
|---|---|---|---|
| `light` | Sweeps, checklist audits, inbox and file triage, data entry, summarizing reading-heavy material. The output is facts, not judgment. | `haiku` for pure reading; `sonnet` when it has to weigh things | Sonnet · `low` (`medium` if it has to weigh things) |
| `standard` | The default. Building, writing, analysis, grading, anything written for the human. | `inherit` (the spawner's model) | Leave the session as opened |
| `deep` | Design decisions others will build on, root-cause hunts, security review, large multi-file changes, a problem with no precedent on the team, and any task where a previous attempt failed | `opus` | The most capable model the picker offers · `xhigh` |

**Picking the tier: the first rule that matches wins.**

1. A previous attempt at this task failed, or a lane failed its rubric grade twice → `deep`.
2. Security review, a design or architecture decision other work will build on, or a bug whose cause is unknown → `deep`.
3. A grader, anything written for the human, or anything touching money, health, legal, or security → `standard` at least, never lower.
4. The work is reading and reporting facts, with no judgment in the output → `light`.
5. Anything else → `standard`.

Torn between two tiers, take the higher one. A wrong `light` costs a redo; a wrong `deep` costs a little extra usage.

**Applying it.**

- **Twins:** pass the model with the spawn (the Agent tool's `model` parameter). Twins can't take an effort level; the model carries the tier.
- **Dispatched sessions:** a session cannot change its own model or effort. The Claude desktop app refuses that, so a session never silently re-prices its own turns. A brief's MODEL TIER line is advisory: switching models needs the human's yes in this session. The Overmind offers the tier in one line when the lane activates (watch rule 2), and applies it from outside, once, only on that yes. Find the session with `mcp__ccd_session_mgmt__list_sessions`: `/go` titles it with the mission ID. Then call `set_session_model` and `set_session_effort` on it (both deferred, so load them through tool search). The model must be an ID the app's picker offers. `get_session` shows the current one, and a wrong ID returns the valid list. The app asks the human to approve a change to a session this one didn't start: one click, and that is the only thing the human does. Record `tier applied` in the board note. No session tools (the terminal CLI, lite mode): tell the human in one line instead. Example: "Nash's lane is tier `deep`: set its model to Opus and effort to Extra high."
- **`standard` changes nothing.** The session runs as the human opened it.
