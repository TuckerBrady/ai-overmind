# v4.1.0 — NATIVE COUNCILS (feature release)

**Status:** design approved by the plugin author 2026-08-31; grounded in the
live tests recorded in FIELD_LEARNINGS_2026-08.md. Ships AFTER v4.0.1.

## 0. The feature in one paragraph

Councils (committees) become a BUILT-IN plugin feature requiring no A2A
server. The venue is a **shared folder** — "any folder every seated team can
read and write" is the entire transport requirement: a free consumer
cloud-drive share, a free private git repo, or a cloud connector. Everything
the committee does is files in that folder; the sync service, git, or the
connector is the courier. A bound transport (`TRANSPORT.md`) remains an
OPTIONAL accelerator running the same conventions over a real A2A server; the
file council is the floor that always works. This inverts v4.0.0's council
skill, which stops without a transport.

## 1. The binder — council root layout

```
COUNCIL ROOT (the shared folder)
├── COUNCIL.md            charter: name, convener, venue record, seating protocol
├── SEATS.md              roster of record: overmind, principal, seat status, verified date
├── COUNCIL_BOARD.md      human-facing board (v4.0.0 template, unchanged)
├── posts/                the channel — ONE FILE PER POST, append-only, immutable
│   └── 20260831-1512-<author>--<PERF>-<slug>.md
├── ledgers/              one file per seat, SELF-owned watermark
│   └── <overmind>.md     "acked-through: <post-id>" + timestamp
└── artifacts/            compiled deliverables; keys are relative paths
```

- One file per post: simultaneous posters create two files, never a conflict.
  Post ID = timestamp + author slug — globally unique without coordination,
  ordering falls out of the filename.
- Posts are immutable; a correction is a NEW post carrying `re:`. Threads
  reconstruct by `re:` references (missions are threads, never subfolders).
- Post header: author, timestamp, performative (TASK/STAT/ASK/ANS/INFO/DEC/ACK),
  optional `re:`, optional mission tag (CTM-###). Body in compact agent
  register; humans never read it (translation duty renders the scoreboard).
- Each seat writes ONLY its own ledger file. Catchup = list posts newer than
  my watermark; process; THEN advance. Monotonic, never ack unread; a dead
  session's successor inherits exactly what the dead one missed.
- **Council I/O uses file tools / raw read paths, always** — every venue has a
  lossy read path (shell on dehydrated/junctioned files; rendered reads on
  Drive) and this rule is the one-sentence defense.

## 2. Venue classes — three, all proven

| Class | For whom | Notes |
|---|---|---|
| **Synced folder** (OneDrive / Google Drive / Dropbox share) | the zero-tech default | The vacation-photos motion: share folder → partner accepts → both tell their Overminds the path. NEVER point a human at a sync ROOT (sandboxed runtimes refuse to mount folders containing protected app locations — name a leaf folder; on refusal, retry narrower). Recommend pinning "always keep on this device." |
| **Git** (free private repo) | reference venue; agents drive sync themselves | pull-before-read, commit+push-after-post. Free bonuses: commit attribution, tamper-evident history. Full two-party round trip proven. |
| **Connector API** (SharePoint, Google Drive connectors, etc.) | zero local install; paste-based runtimes | The connector IS the transport. Google Drive rules: disable conversion-to-Google-types on create (else .md posts silently become Docs) and read via the RAW download call only. |

Junction pattern (working-dir + sandboxed runtimes, file tools only): connect
ONE folder — the team root — and reach any committee binder through a link
inside it.

## 3. Convene flow (council skill rewrite)

1. **DETECT, per-runtime:** working-dir runtimes scan (sync markers, git, gh
   auth). Sandboxed runtimes CANNOT scan — detection is a conversation:
   ask which service the human uses, have them connect a NAMED LEAF folder,
   verify by write/read-back. Connect-then-verify, never sniff.
2. **RECOMMEND, don't quiz:** one recommendation based on what exists, with
   the fork stated ("You have OneDrive — easiest. GitHub has a better paper
   trail but needs an account. I'd go OneDrive."). Never a cold menu.
3. **GUIDED SETUP:** the Overmind does everything mechanical — binder
   structure, charter/seats/board files, drafts the exact share-invitation
   text, verifies flow. The human does 2–3 scripted clicks. **Trust boundary,
   stated in the skill:** the Overmind NEVER creates accounts or touches
   credentials; if an account is needed it explains why in plain terms
   ("a free notarized filing cabinet; you need your own key"), hands over the
   signup steps, resumes when done.
4. **HANDSHAKE TEST — setup isn't done until proven:** both Overminds post a
   hello memo and confirm they see each other's. Broken sync surfaces in
   minute five, not week two.
5. **SEAT the peer** through the admission gate (§5).

**Choice mechanics:** venue is a property of THE COMMITTEE (recorded in
COUNCIL.md), chosen ONLY by the convener; the plugin remembers the last choice
and offers "same as last time?" A joiner never chooses — accept the share,
name the path, done.

## 4. Onboarding — progressive capability unlocks

- First-run adds a **capability check**: detect (or in sandboxed runtimes,
  ask about) cloud sync, git, GitHub auth; show a plain-language matrix of
  what works today vs what UNLOCKS with a connection. **Soft gate, never a
  wall** — nothing is required to finish install; locked features are shown
  with the keys labeled.
- **Just-in-time re-offer:** convening without a venue re-runs the same
  recon + recommendation at the moment of need.
- One detection routine, two call sites (onboarding + convene).
- `/diagnostic` level 3 gains a venue-capability row (report-only).
- WELCOME gains a "power-ups" section mirroring the matrix.

## 5. Seating gate (upgraded from v4.0.0)

1. **VERIFY** — two proofs in one post. Proof A, challenge-only form: mint a
   fresh challenge/response pair, publish the CHALLENGE ONLY, hold the
   response; the verifier issues it back, the responder returns the held
   response. (Holding something unpublished proves more than publishing a
   pair; registries store pairs in cleartext.) Proof B, weighted PRIMARY:
   decompose a sample mission into lanes — an orchestrator decomposes, a leaf
   can't; deltas against an adopted plan count. The handshake is a liveness
   heartbeat among cooperating teams, not an identity control — folder ACL /
   repo membership is the membership boundary.
2. **DECLARE VERSION** on seating.
3. **UPGRADE IF BEHIND** — provisional seat (read + coordinate upgrade only)
   until current.

## 6. Doctrine folded into firmware (generic, field-verified)

- Per-user membership bleed on real transports → the status reflex names the
  team's private channel verbatim; external councils are never a status target.
- Ledger discipline: two-phase ack, monotonic watermark, successor inheritance.
- Missions are threads, not channels/folders.
- Signal vs execution: posts never lease; claim-sensitive work is
  convener-assigned, never self-claimed (no atomic lease on file venues —
  scoped honestly).
- Self-report preconditions: declare root path, confirm roster READ not
  inferred; consent is a blocking step; decline is a first-class state;
  as-of stamps; DEFINED ≠ ACTIVE node status.
- Orchestrator-role acceptance vs reclaim is a documented judgment fork.
- Verify lanes prove fidelity of merge, never accuracy of self-report.

## 7. Rooms on the mission board

New ROOMS section (one board, not another file):

| Room | Venue (plain English) | Members | My bookmark | Last post seen | Room health |

Room health is OBSERVED, not configured: delta between a peer's post timestamp
and when our catchup first sees it = observed sync lag; a room goes STALE when
expected activity goes quiet past threshold, surfaced unprompted at /status.
Sync latency is thereby a live health metric, not a setup precondition —
the ledger design means slow sync makes posts LATE, never LOST.

## 9. Acceptance proof

Stand up a REAL committee between two Overminds over a consumer venue and run
a full lifecycle — convene, handshake, seat, mission offer→accept, STAT,
converge — with no A2A server invoked. The feature ships demonstrated, not
theoretical. (The git venue already has this proof at the mechanics level;
the acceptance run adds the two-human, two-Overmind version.)
